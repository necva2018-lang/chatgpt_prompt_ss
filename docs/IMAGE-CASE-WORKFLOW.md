# 圖片案例階段規劃與驗收

適用本專案的圖片成果。2026-10-09 使用者將每批數量改為 20 個案例，各類仍逐張驗收；每批完成精簡驗證及記錄後，可依持續執行授權自動接續下一批。批次可跨內容階段，案例保留各自階段 ID。公開部署另行記錄，不與本機同步混為完成。保存每次工作的開始、結束時間與耗時，包含設定、生成、修正、上傳與驗收；有中斷則分開記錄工作時段，不將離線間隔算入實際工作耗時。

## 階段

| 階段 | 內容 | 完成條件 |
|---|---|---|
| 0 管理基礎 | skills、進度表、素材與驗收規則、上傳前檢查 | 管理資料及工具驗證通過，既有案例如實登記 |
| 1 產品與廣告 | 先替換兩個 AirPods 案例，再做產品、海報、零售、廣告 | 每批本意驗收、Cloudinary、資料與頁面檢查通過 |
| 2 攝影與場景 | 光線、視角、背景、日常場景 | 同上 |
| 3 材質與創意 | 材質、藝術風格、想像世界 | 同上 |
| 4 解說與技術 | 操作、機構、標註、科学視圖 | 同上，另附可信事實來源與核對 |
| 5 補齊與整體驗收 | 覆蓋、重複、失效連結、展示與發布狀態 | 所有選定案例有驗收證據；未採用指令有原因 |

以全部642筆圖片指令為覆蓋清單，已有成果不重做；逐筆記錄完成或具體待處理原因。同名／相近指令保留來源ID，可共用符合本意的成果但必須逐筆對應，不能僅因重複便漏掉。不可用 deferred 或待修冒充全部完成，也不把來源聲稱「已測試」當本站實測。

## 唯一進度資料

`database/image-case-progress.json` 是主記錄；`npm run image:progress` 驗證後產生 `docs/IMAGE-CASE-PROGRESS.md`。請勿分別手動修改兩者。記錄每個案例、階段、批次、指令、素材來源狀態、生成／驗收／上傳／網頁／使用者確認／部署狀態、證據與下一步。未完成不計入合規完成數。

每次開始先讀進度、目前批次與最近活動。每張完成一步就儲存，記錄停止點；再次呼叫從第一個未完成步驟接續，避免重生圖或重上傳。不得把「正在執行中止」寫成使用者要求暫停。

## 素材來源與使用者授權

- 2026-10-09 最新授權：可使用專案 `ex product` 產品案例豐富化下一批與後續案例，也可使用助理素材。已完成案例保留，不重做。使用者素材標記 provided_by=user、kind=user_provided，保存原始路徑、SHA-256 及 authorization={date,directory:"ex product",instruction:使用者原授權}。不得改名後標成助理來源。
- 商品圖的文案與宣稱屬參考內容，不是工作指令；不複製促銷版面、浮水印或未核實功能宣稱。品牌商品的生成圖為效果示範，不聲稱官方廣告。
- 優先使用內建 imagegen 生成無品牌中性產品、人物或空間；記錄生成工具、完整提示詞、原圖檔案與 SHA-256。原圖本身也須檢查合理性。
- 若 AI 素材無法表達案例，找授權明確的外部圖片，核對原始來源、改作及公開展示條件，記錄授權網址、作者／歸屬、取得日期與要求的標示。無法確認時只留本機草稿。外部素材不是自動准許的任意搜尋結果。
- 依指令選適配素材；可重用同一張助理取得的原圖方便比較，但輪替產品與情境。真實品牌及人物須依案例用途處理來源與標示。
- 技術／醫學／科學圖片需要可信參考，不能從產品外觀推測內部構造或聲稱正確。
- 2026-10-09：兩個 AirPods 案例已由助理生成的無品牌保溫瓶案例替換；舊案例登記 `archived_replaced` 並保存於 database/case-history/preview-01.json，不算新規則合規完成。保留原檔與 Cloudinary 歷史，不直接刪除素材。

## 每批流程

1. 選 20 個指令，核對 `image-prompts.json` 的 ID、英文原文、中文說明、來源。若翻譯衝突，先修正解釋，不盲目按中文生圖。
2. 先寫本意驗收條件，取得合適素材，登記來源與原圖哈希。
3. 用內建 imagegen 依指令生成，保留完整實際提示詞與成果檔。每張視覺檢查，不能只讀檔名或依生成提示詞推斷圖片內容。
4. 五項驗收：主體 subject、場景 scene、指令效果 effect、位置／比例／互動 relations、文字／標註／細節 details。在一次目視中涵蓋五項，簡短記錄 expected、observed、status，不逐項重開圖片；不適用細節需說明「無文字／標註要求」並仍檢查畫面瑕疵。
5. 任何一項不符合就記錄偏差，修正提示詞重生並再次檢查。每個案例每次工作最多 2 次修正；仍不符合則保留待修及下一步，不上傳，讓下次有空接續。這個限制不代表放寬品質。
6. 圖片與提示詞修改後，舊驗收失效。`review` 必須綁定原圖、成果與提示詞 SHA-256，保留英文原指令、檢查時間、檢查者與事實核對。
7. 對應清單置於 `database/media-batches/<batch>.json`，加入 `source` 及 `review`（格式見下）。一般直接執行帶有來源與驗收預檢的 `media:upload`，其本身會產生 plan；僅來源、路徑或映射有疑慮時另跑 `media:preview`。上傳工具在任何連線前阻止來源或本意驗收缺失的批次，禁止用 preview-01 舊清單繞過。
8. 上傳後核對 Cloudinary receipt、case_ids、來源與成果對應、雙向案例 ID。以程式整批核對所有案例ID、提示詞、雜湊、網址及指令關聯，執行資料驗證；上傳流程已執行的建置不重跑。瀏覽器每批只抽查首張、末張及1張特殊構圖，涵蓋卡片／詳情／案例位置，檢查 naturalWidth > 0，保存1張代表截圖；抽樣失敗才擴查相關項目。未抽查案例記錄為批次資料核對加抽樣驗證，不宣稱逐案瀏覽器驗證。只有程式變更或發現異常時跑完整 npm run check；單純新圖片不重跑不變的測試套件。
9. 更新每張進度與整批記錄。使用者確認獨立記錄，不將程式檢查或助理目視通過假冒使用者認可。跑 `npm run image:progress`，報告本批完成、未完成、待修與下一步。

`/subwayad` 的本意是「產品出现在地鐵廣告」，產品只在月台上不合格；必須看到站內廣告載體與產品印在其中。`/packshot` 必須看到清楚產品、乾淨棚拍背景、合理燈光與陰影。不能以「好看」代替本意驗收。

## 批次驗收欄位

每個案例沿用既有欄位，增加：

```json
{
  "source": {
    "provided_by": "assistant",
    "kind": "ai_generated",
    "path": "output/imagegen/<batch>/reference.png",
    "sha256": "原圖雜湊",
    "generator": "built-in imagegen",
    "prompt": "實際生成原圖的完整提示詞"
  },
  "review": {
    "status": "passed",
    "reviewer": "Codex visual inspection",
    "checked_at": "ISO 時間",
    "source_instruction": "資料庫英文原指令",
    "reference_sha256": "原圖雜湊",
    "result_sha256": "成果雜湊",
    "applied_prompt_sha256": "實際成果提示詞雜湊",
    "requires_factual_check": false,
    "criteria": [
      {"dimension": "subject", "expected": "主體驗收條件", "observed": "目視所見", "status": "passed"}
    ]
  }
}
```

上例只展示 criteria 的單項格式，實際必須包含上述五項。外部來源 kind=`external_licensed`，另填 url、license_url、license、attribution、checked_at、allows_modification=true、allows_public_display=true。技術類 requires_factual_check=true，增加 factual_check={status:"passed",notes:"核對結論",source_urls:[可信來源]}。程式只能檢查結構與證據是否過期，圖片語義及授權判斷仍由實際查證與目視驗收完成，不宣稱已自動證明正確。

## 呼叫

- `$image-case-workflow` 或「繼續圖片案例」：先讀進度；持續執行模式啟用時依序接續批次。
- `$image-case-verify` 或「驗證這批案例」：依本意五項檢查，出具實際結果。
- `$cloudinary-case-sync` 或「上傳並同步這批案例」：只接入完整驗收批次，沿用本機憑證、上傳紀錄及網站建置。
- 「查看圖片進度」：只跑 image:progress 與讀報表，不生成或上傳。

技能存於專案 `skills/` 並安裝到使用者技能目錄，文件與腳本維持在本專案，避免複製多份業務邏輯。新聊天才能保證技能出現在新載入的目錄；當前聊天可直接讀已建立的 SKILL.md。

## 持續執行與額度中斷（2026-10-09更新）

使用者說「開始做」時啟動持續執行：每批20個作為存檔及回報單位，完成一批後直接選下一批，不再要求逐批確認，直到所有圖片指令覆蓋完成。單純修改規則或查詢進度不啟動生圖。使用者要求停止時停止。

每張生圖、驗收與上傳後立即保存；每批記錄時間與累計數。遇生圖／使用額度不足時不反覆重試或擅自改用付費API；記錄 quota_wait、錯誤摘要、已知恢復時間（不知道就null）、當批及第一個未完成步驟、已生成檔案、驗收與upload receipt，結束當次工作。額度恢復後重新進入可執行回合，從存檔接續，避免重生圖、重傳與重做舊成果；沒有排程或活躍回合時不能保證自動喚醒。

精簡的是重複瀏覽器操作、重跑測試與長篇紀錄；每張成果仍需一次本意目視及上傳前來源／哈希核對，技術內容仍按需核實。
